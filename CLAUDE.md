# samplr: context for Claude

## The project
Desktop audio sample manager for **macOS and Linux**: listen to, tag and organise samples (for musicians, alongside a DAW).

## How we work
- Move forward in **small steps that compile and run**: each step must be testable with `cargo run`.
- **Everything in the repository is in English**: identifiers, comments, user-facing messages, command names, documentation and commit messages.
- Keep the code simple and readable rather than advanced-idiomatic. No premature abstraction.
- When a compiler error is pasted, explain it before fixing it.
- Before handing back: `cargo build`, `cargo clippy` and `cargo fmt` without warnings.
- Think Mac **and** Linux for every choice (paths, audio, drag and drop, packaging).

## Current stack
- Rust edition 2024, single `samplr` binary (command line for now).
- `symphonia` 0.5 (feature `all`): file info and decoding. **Keep 0.5**, it is the version `rodio` uses; moving to 0.6 would compile two versions.
- `rodio` 0.23 (feature `symphonia-all`): audio playback. API: `DeviceSinkBuilder::open_default_sink()`, `Player::connect_new(mixer)`, `Decoder::try_from(file)`.
- `walkdir`: recursive folder walking.
- `rusqlite` 0.41 (feature `bundled`: SQLite compiled with the project, no system library to install). No `usize` in queries: rusqlite cannot convert it, use `u32` or `i64`.
- `dirs`: the system's standard data folder.
- `dunce`: use `dunce::canonicalize`, never `Path::canonicalize`. Identical on Mac and Linux; on Windows it avoids `\\?\C:\…` paths, unreadable and different from the ones `notify` reports. Likewise, never hard-code `/` as a separator (`std::path::MAIN_SEPARATOR`).
- `notify-debouncer-full` 0.7 (re-exports `notify` 8): folder watching. Groups the events of a single file for 1 s, and matches both ends of a rename (`RenameMode::Both`), including on Mac where FSEvents sends them separately.
- `clap` 4 (feature `derive`): subcommands are described by the `enum Command` in `main.rs`; the `///` comments become the `samplr help` output.

- Debug builds compile the **dependencies with optimisations** (`[profile.dev.package."*"]` in the root `Cargo.toml`): unoptimised, symphonia decoded an MP3 about 30 times slower (waveform of a 54 s MP3: 2.3 s, 0.24 s with this setting, 0.07 s in release). Costs a few minutes once, after a `cargo clean` or a dependency update; our own code still rebuilds in about a second.

Linux system dependencies: `build-essential pkg-config libasound2-dev` (ALSA).

On the Mac, the project is opened from the Linux machine's SMB share (`/Volumes/nico/Sites/projets/sample browser`). The share does not support the file locking Cargo needs ("could not create session directory lock file"): the Mac's `~/.cargo/config.toml` therefore sends the build to `/Users/nico/cargo-target` (`build.target-dir`), which also avoids mixing macOS and Linux binaries in `target/`. Do not put this setting in the project's `.cargo/config.toml`: the path does not exist on Linux.

## Current state (step 6 done)
`src/main.rs` holds the commands, `src/lib.rs` the shared code (file reading and indexing), `src/db.rs` the database access, `src/waveform.rs` the waveform computation and drawing, `src/watch.rs` the folder following:
- `samplr scan <folder>`: lists the audio files (wav, aif, aiff, flac, mp3, ogg, m4a) with length, sample rate, bits and channels, and saves them to the database (absolute path; a new scan updates without duplicates and keeps the `id`, hence the tags). Unreadable files are counted, without crashing. AppleDouble `._*` files left by macOS are ignored.
- `samplr list`: shows the samples in the database, with their tags between brackets. Output goes through `writeln!` rather than `println!`: `samplr list | head` stops without error when `head` closes the pipe ("broken pipe"), and `scan` runs to the end even if its output is cut off.
- `samplr tag <file> <tag>...` / `samplr untag <file> <tag>...`: adds or removes tags. `tag` reads the file again and adds it to the database if it was not there.
- `samplr tags`: the tags and how many samples carry each.
- `samplr fav <file>...` / `samplr unfav <file>...`: marks samples as favorites or no longer (`fav` adds a file to the database if needed, like `tag`). `samplr search --fav` keeps only the favorites; `list` and `search` show a ★ before a favorite.
- `samplr folders`: the scanned folders and how many samples each holds. `samplr remove-folder <folder>`: the folder is no longer followed and its samples are **hidden**, not deleted: they leave the list (search, `list`, `tags`, waveform computing) but keep their row and their tags, which come back if the folder is scanned again (`db::save` sets `hidden` back to 0). Their waveforms are deleted. A sample still inside another scanned folder stays shown. The audio files are never touched.
- `samplr watch`: first catches up with the changes made while it was not running (vanished samples removed, new ones added), then follows the scanned folders live until Ctrl+C. A rename or a move, of a file or a folder, keeps the `id` hence the tags. A scanned folder inside another one is watched only once.
- `samplr search [tag]... [--path <text>]`: samples carrying **all** the given tags, whose path contains the text (case-insensitive, `_` taken literally).
- `samplr play <file>`: plays a file on the default output.
- `samplr wave <file> [--width N]`: draws the waveform in the terminal, computing and caching it first if needed.
- `samplr waveforms`: computes every missing or stale waveform (about 0.6 s for 10 min of audio in release). `scan` does not compute waveforms: decoding every file would make it much slower on a big library.

Database: `samplr.db` in the system data folder (`~/.local/share/samplr` on Linux, `~/Library/Application Support/samplr` on Mac). The `SAMPLR_DB` variable points to another database, for experiments. Tables `files` (with `hidden`, see `remove-folder`, and `favorite`), `tags`, `file_tags`, `folders` (the folders given to `scan`, followed by `watch`), `waveforms`, `collections` and `collection_files` (samples gathered by hand; a sample forgotten by the database leaves its collections, a hidden one stays in them and comes back with its folder). Schema changes go through `db::migrate`: SQLite keeps the schema version (`PRAGMA user_version`, 3 so far), each step runs once, under `BEGIN IMMEDIATE` so that the app and a command opening the database together do not both run it. A new database goes through every step too (the `CREATE TABLE`s are version 0): add a column with a migration step, not in the `CREATE TABLE`. A waveform is 1024 (min, max) peaks over all channels, stored as signed bytes (2 KB), with the file's size and modification date: if either has changed, the waveform is stale and computed again. Peaks are built on the fly by merging buckets two by two, so memory use does not depend on the file length, which is not always known in advance (some MP3s). Tags are stored lowercase, without spaces; a tag no longer used by any sample is deleted. **Unplugged disk**: if the scanned folder itself has disappeared, nothing is removed from the database, at startup or live. Otherwise unplugging an external disk would erase the tags of all its samples.

Scanning and playback have been tested on Linux and on the Mac (files read from the SMB share).

Audio pitfalls met so far:
- `sleep_until_end()` returns before the sound card's buffer is drained: without the 300 ms pause that follows in `play`, a very short sample (75 ms kick) is dropped without being played.
- An HDMI output suspended by PipeWire takes one to two seconds to wake up and swallows a short sample. Not a samplr bug: fix it on the system side, with a WirePlumber rule `session.suspend-timeout-seconds = 0` on the output concerned.
- Mac, file on the SMB share: an "audio stream error: A buffer underrun or overrun occurred" appeared once (not reproduced in 6 attempts). Likely cause: `Decoder::try_from(file)` reads the file chunk by chunk during playback, hence over the network. Edge case (the share is only used for testing): playback keeps streaming from disk. Loading the file into memory would delay the start of long files, which would hurt quick previewing from one sample to the next.
- Mac, HDMI output (DELL U2415 monitor): macOS has no volume control for an HDMI output, sound goes out at full level. SoundSource adds a software volume, but applies it **per app**: a program launched from the command line (`samplr`, `afplay`) is attached to the terminal that launched it. Launched from iTerm2, `samplr` shows up under "iTerm2" in SoundSource and follows its volume: not a `cpal`/rodio problem. The loud sound came from launches in another terminal, whose SoundSource entry was not attenuated. A samplr volume control (`Player::set_volume`) is still useful for the interface.
- Apple `.m4r` ringtones (AAC in MP4, e.g. `/System/Library/PrivateFrameworks/ToneLibrary.framework/Versions/A/Resources/Ringtones/Opening.m4r`) are not decoded by symphonia 0.5: length found, channels unknown, no sample. The same sound re-encoded by `afconvert` (AAC or WAV) plays fine: AAC is supported, the structure of these files is the problem.
- When the decoder produces no sample, `play` reports it ("no sound decoded"): it checks this on a throwaway decoder before opening the audio output.

## Roadmap
1. ✅ Scan a folder and list the samples.
2. ✅ Preview: `play` tested on Linux and on the Mac. Volume: in the interface only (step 7).
3. ✅ **SQLite** database (`rusqlite`): files, tags and link tables. Tags stay in the database, never in the audio files.
4. ✅ CLI commands to tag and search, with `clap`.
5. ✅ Folder watching (`samplr watch`, and the interface while it is open), tested on Linux only. Remaining: test it on the Mac (renames). Removing a folder: `samplr remove-folder` and the interface's Folders window.
6. ✅ Waveform computation and cache in the database. The interface computes the missing ones in the background; `samplr watch` does not.
7. ⏳ Graphical interface with **Tauri** (Rust backend + web interface), keyboard preview. See "Step 7 in progress" below.
8. ⏳ Drag and drop of samples into the DAW: written with `tauri-plugin-drag` (native drag and drop on Mac, Linux and Windows). Tested on Linux into Nautilus, a terminal and Bitwig; to test on the Mac. **Linux pitfalls**: the `drag` crate (under the plugin) is patched in `vendor/drag` (`[patch.crates-io]` in the root `Cargo.toml`): it did not escape file URIs (a `#` or a space broke the path) and disconnected its handlers before the receiver asked for the file (upstream issue crabnebula-dev/drag-rs#84). Under Wayland, GTK 3 answers only the first request for the file and the drop arrives empty: the app therefore sets `GDK_BACKEND=x11` at startup (XWayland) unless the variable is already set. The page cancels `dragstart`, otherwise WebKit starts its own drag alongside the native one. A drag starts after the mouse moves 5 pixels with the button held, so a click still selects and plays; the file is offered as a copy (`mode: "copy"`), never moved; the drag image is the sample's name drawn on a canvas. The plugin's JavaScript API is `window.__TAURI__.drag` (global API script, no npm), allowed by `drag:default` in `src-tauri/capabilities/default.json`.
9. ⏳ Favorites ✅ (a `favorite` column, not a tag: a decision taken). Collections ⏳: samples gathered by hand (not saved searches: a decision taken), with multiple selection and dragging rows onto a collection. Remaining: automatic analysis (BPM, key).
10. Settings panel. Among the settings: whether to ask for confirmations (deleting a collection, removing a folder; removing samples from a collection is not confirmed).
11. Packaging: signed and notarised `.app` / `.dmg` on Mac, AppImage or `.deb` on Linux.

## Step 7 in progress (7a to 7d done, tested on Linux)
- Tauri 2 stable (2.12.x at the time of writing; 3.x is only in alpha).
- Fedora packages Tauri needs (installed on the Linux machine): `webkit2gtk4.1-devel libsoup3-devel gtk3-devel javascriptcoregtk4.1-devel libappindicator-gtk3-devel`. Already present: `openssl-devel`, `librsvg2-devel`. Node and npm are available through nvm.
- Layout: the crate is a library (`src/lib.rs`: `db`, `waveform`, `SampleInfo`, `read_info`, `index`; done) plus the CLI binary (`src/main.rs`, `use samplr::…`). The Tauri app lives in `src-tauri/`, in a Cargo workspace declared in the root `Cargo.toml` (one `Cargo.lock`, one `target/`).
- Preview is played on the Rust side with rodio, not by the web view: every format symphonia reads is supported (WebKitGTK lacks some, e.g. AIFF), and an output kept open for the whole session avoids the short-sample problems listed above.
- Planned sub-steps:
  - 7a: library + CLI + workspace, then a first Tauri window.
  - 7b: sample list, search, keyboard navigation, preview played by Rust.
  - 7c: waveform display from the peaks cached in the database.
  - 7d: adding and removing tags from the interface.
- Decisions taken: plain HTML, CSS and JavaScript in `ui/`, no build tool and no Node (`withGlobalTauri` exposes the API as `window.__TAURI__`); waveform drawn on a `<canvas>` from the cached peaks, no wavesurfer.js.
- Run the interface with `cargo run -p samplr-app`; `cargo run` alone still runs the CLI. No Tauri CLI needed for development. `src-tauri/icons/icon.png` is a placeholder icon.
- 7b: one search box (each word must be in the path or in one of the tags; a `#tag` word requires that exact tag), the list of results, ↑ ↓ to move and play, Enter to replay, Esc to stop, a click plays. An audio thread opens the output once for the whole session and gets the sounds to play through a channel; each sound gets a new `rodio::Player`, dropping the previous one cuts it. The file is opened by the `play` command, so an unreadable file is reported to the page.
- 7c: the selected sample's waveform is drawn on a `<canvas>` above the list, at the screen's real resolution. `samplr::peaks` (in `src/lib.rs`, shared with `samplr wave`) returns the cached peaks or computes and caches them. A late answer for a sample no longer selected is ignored.
- 7d: a tag bar under the waveform shows the selected sample's tags, each with a × to remove it. Ctrl+T (Cmd+T on Mac) moves to the tag box; there, Enter adds the tags typed (separated by spaces), Backspace on an empty box removes the last tag, Esc goes back to the search box. The `add_tags` and `remove_tag` commands return the sample's tags after the change.
- Preview controls: Play, Play loop, Stop (same as Esc) and a volume slider in the header. "Play loop" turns loop mode on: every sample selected afterwards also plays in a loop, until "Play" brings back single playback (Stop does not change the mode). A loop uses rodio's `build_looped`, which seeks back to the start of the file at each end instead of keeping the sound in memory; the audio thread receives either decoder as a `Box<dyn Source + Send>`. The slider's position is squared before reaching rodio (`set_volume` command, 0.0 to 1.0), so that it acts evenly over its whole travel (a linear slider barely changes the loudness in its top half); it is remembered in the web view's `localStorage`. The audio thread receives `AudioRequest::Play`, `Stop` or `Volume`, and applies the volume to the sound playing and to the next ones. It waits for requests at most 100 ms at a time, to notice when the sound has played to its end: it then sends the page a `playback-ended` event with the number the page gave to that sound (`play` command's `id`), and the page ignores the end of a sound already replaced by another one. The audio thread is started in Tauri's `setup`, to get the `AppHandle` it sends events with.
- Playhead: a line over the waveform (a `<div>` moved in CSS, not a redraw of the canvas). The audio thread sends a `playback-position` event every 100 ms (`Player::get_pos`); in between, the page moves the line on the clock (`requestAnimationFrame`). In loop mode the position is taken modulo the sample's length. No line when the length is unknown (some MP3s).
- A click on the waveform plays the sample from that point (`play` command's `start`, applied with `Player::try_seek` right after `append`), in the current mode (once or loop). Ignored when the length is unknown.
- Adding a folder: the "+ Folder" button opens the system's folder chooser (`tauri-plugin-dialog`, JavaScript API `window.__TAURI__.dialog`, allowed by `dialog:default`), then the `add_folder` command scans it like `samplr scan`: both call `samplr::scan` (in `src/lib.rs`). Progress bar: `samplr::scan` first counts the audio files (`count_audio_files`, a walk that reads no file), then `index` calls a callback after each audio file, readable or not; `add_folder` turns it into `scan-progress` events (`done`, `total`), at most one every 100 ms, shown as a `<progress>` in the status line. Until the first event the bar shows an activity without a value. The folder is followed live from then on.
- Live following: while the app is open, the scanned folders are followed like `samplr watch` (catch-up at startup, then live changes; renames keep the tags; an unplugged disk is left alone). The code is shared: `src/watch.rs` in the library (`roots`, `new_watcher`, `catch_up`, `handle_event`), which reports what changed through a callback; `samplr watch` prints it, the app (`src-tauri/src/library.rs`) sends the page a `library-changed` event after each batch of changes, and the page searches again, keeping the selected sample and the sound playing. If the selected sample left the library (folder removed, file deleted or renamed) and is the one playing, its sound stops; a sound only left out by the current search keeps playing. `Library` (in `State`) holds the watcher and the watched folders, so that `add_folder` watches a new folder at once (`update_watched`). Running `samplr watch` at the same time works but is useless: both apply the same changes.
- Folders window ("Folders…" button, a `<dialog>`): the scanned folders with their sample count, "(not found)" when missing from disk, and a Remove button each, confirmed through `window.__TAURI__.dialog.ask` (the plugin's `message` command, allowed by `dialog:default`). Commands `folders` and `remove_folder` (which also stops watching the folder, through `Library::update_watched`). While the window is open, the list's keys are off.
- Dropping on a collection: rows dragged out of the list (the native drag of `startDrag`) or files from a file manager, dropped on a collection of the left column, are added to it. The page learns of the drag only through Tauri's drag-and-drop events (`getCurrentWebview().onDragDropEvent`: enter, over, drop, leave), whose position is in physical pixels (divided by `devicePixelRatio` for `elementFromPoint`); each collection's `<li>` carries `data-id`. The collection under the cursor is outlined. `add_to_collection` leaves out the paths not in the library (files from elsewhere, folders) and reports how many (`unknown`).
- Sorting: a click on a column header (★, Name, Folder, Length, Tags) sorts the list, a second click reverses it (▲/▼ on the header). Done in the page (`sortSamples`), kept across searches and refreshes; with no column chosen, the database's order (by path). Natural order, case ignored (`Intl.Collator` with `numeric`): "kick 2" before "kick 10". Missing values (unknown length, no tag) stay last whichever the direction; equal values fall back to the path.
- Multiple selection: click selects one row, Ctrl/Cmd+click adds or takes out a row, Shift+click and Shift+↑↓ select from the anchor (the last row clicked without Shift) to the row. The page keeps `selected` (the current row: played, waveform shown, outlined when several are selected), `selectedPaths` (paths rather than rows, so that a refresh keeps the selection) and `anchor`. Tags (the tag bar shows the tags common to the selection), Ctrl+D (all become favorites, unless all already are), the collection commands and Del act on the whole selection; the ★ of a row and its × in a collection act on that row only. Dragging a selected row drags the whole selection to the DAW (the drag image says how many); dragging a row outside the selection drags that row alone. A right-click inside the selection keeps it. `add_tags`, `remove_tag` and `set_favorite` take a list of paths and work in one transaction.
- Favorites: a ★/☆ column at the start of each row (a click toggles it without selecting nor playing), Ctrl+D / Cmd+D toggles the selected sample, and a "★ Favorites" button filters the list (`search` command's `favorites`). Command `set_favorite`. With the filter on, a sample no longer a favorite stays in the list until the next search.
- Collections: the column on the left lists "All samples" then the collections, each with its number of samples; a click opens one in the list (search and Favorites filter apply within it). The form at the bottom creates an empty one. A right-click on a row selects it without playing and opens a menu (`#context-menu`, built in the page): add to a collection (those already holding the sample are shown with ✓, greyed and not clickable, with a × next to them that takes the selection out: `collections_holding` command, which returns the collections holding **all** the given samples), add to a new collection named in the menu (adding, × and a new collection keep the menu open and redraw it with the new state; only a click elsewhere or Esc closes it), and, in an open collection, remove from it. Del (Backspace on a Mac keyboard) also removes, when the focus is not in a text box, and so does the × at the end of each row (that row's sample, selected or not). After a removal the list is refreshed keeping the selection, and the sound keeps playing (`refresh({ stopIfGone: false })`). Removing is not confirmed (only links go); deleting a collection (×) is. Commands `collections`, `create_collection`, `delete_collection`, `add_to_collection`, `remove_from_collection`; `search` takes the open `collection`. No CLI command yet. The column folds into a thin strip (‹ / › button, Ctrl+B / Cmd+B), remembered in `localStorage` like the volume.
- Background waveforms: a thread of `Library` computes every missing or stale waveform (`samplr::update_waveform`, shared with `samplr waveforms`) after the startup catch-up, after each batch of changes on disk and after `add_folder`. Wake-ups that come during a pass are merged into one more pass. Unreadable files are tried again at each pass (nothing is cached for them). The page's `waveform` command still computes a waveform not ready yet; both may compute the same one, harmlessly (`INSERT OR REPLACE`).
- Rust functions called from the page are marked `#[tauri::command]` in `src-tauri/src/main.rs` and listed in `generate_handler!`. They return `Result<T, String>`: the error must be serialisable to reach JavaScript, `Box<dyn Error>` is not.

## Known limitations
- Path case: on Mac (by default) and on Windows, `Kick.wav` and `kick.wav` are the same file, but the database compares paths as case-sensitive text. A rename that only changes case, or a path typed with another case in `tag`, may not find the sample. Needs a design decision.

## Design decisions
- **Never move audio files without an explicit user action**: DAW projects point to their paths. Prefer virtual collections (tags, favourites, smart folders).
- App data in the system's standard folder (`~/.local/share` on Linux, `~/Library/Application Support` on Mac), through the `dirs` crate.
